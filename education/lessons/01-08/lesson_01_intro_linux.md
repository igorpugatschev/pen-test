# Занятие 1: Введение в Linux для пентестера

## Учебная рамка

**Входные требования:** Минимальные знания процедурного Python, базовое понимание файлов и папок, доступ к Terminal на macOS.

**Результат занятия:** Студент понимает, зачем Security QA/SDET нужен Linux-подход к рабочей среде, создает локальное evidence-пространство и объясняет, чем macOS native, Kali ARM64 VM и cloud lab отличаются по назначению.

**Наследуемая SDET-компетенция:** профессиональная рабочая среда, воспроизводимость действий, аккуратные артефакты, привычка фиксировать фактический результат.

**Security QA-компетенция:** безопасная подготовка рабочей станции, локальное хранение evidence, разделение учебной среды, тестового стенда и production.

**Связь с книгами:** материал урока составлен на основе локально проиндексированных книг: «PyCharm. Профессиональная работа на Python 2024» — рабочая станция, Git, виртуальные среды, удаленная Linux-среда; «Легкий способ выучить Python 3 еще глубже» — настройка инструментов, терминал, записная книжка, 45-минутная практика; «Объектно-ориентированный Python» — дисциплина организации проекта и понятные границы ответственности.

**Основной источник:** «PyCharm. Профессиональная работа на Python 2024» и «Легкий способ выучить Python 3 еще глубже».

**Дополнительные источники:** «Объектно-ориентированный Python» для аккуратной структуры локальных helpers.

**Что берем из источника:** не список страниц для самостоятельного поиска, а готовые учебные идеи: рабочая станция должна быть воспроизводимой; инструменты должны быть проверены до практики; заметки и evidence нужны с первого занятия; среда выполнения влияет на поведение программ.

**Как это превращается в SDET/Security QA навык:** студент учится готовить рабочую станцию так, чтобы любой безопасный тест можно было повторить, объяснить, приложить к задаче и не смешать с действиями вне scope.

**Что нельзя переносить на Slider AI без отдельного разрешения:** активное сканирование, перебор, payload-тесты, изменение данных, нагрузочные проверки и любые действия вне `https://olddev.slider-ai.ru`.

**Процессный артефакт:** `Security QA workstation readiness note` — короткая заметка о среде, структуре папок, разрешенной цели и правилах evidence.

**Безопасная цель:** локальная домашняя директория студента, специально созданная папка `~/slider-ai-pentest` и тестовый стенд `https://olddev.slider-ai.ru` только как записанная в заметке разрешенная цель. В этом уроке сайт не тестируется.

**Среда выполнения:** обязательный путь новичка — macOS native. Kali Linux ARM64 VM в UTM/VMware Fusion/Parallels — углубление, когда нужно изолировать Linux-инструменты. Cloud lab — для тяжелых или экзаменационных сценариев.

**Обязательный путь новичка:** создать локальное evidence-пространство, выполнить безопасные команды просмотра среды и оформить заметку урока.

**Углубление:** описать, когда нужна Kali ARM64 VM, какие ресурсы дать VM на MacBook Air M2 8GB и зачем делать snapshot.

**Минимальная проверка успеха:** есть папка `~/slider-ai-pentest`, файл `notes/lesson_01.md`, вывод `pwd`, `uname -m`, `sw_vers` или безопасный аналог для выбранной среды.

**Эталонный вывод:** в артефакте есть команда, фактический вывод, краткая интерпретация и строка `Status: observation`.

**Критерии сдачи:** зачет — создан workspace и оформлен evidence; хорошо — объяснена разница macOS/Kali/cloud lab; отлично — добавлена политика, какие действия требуют approval.

В каждом упражнении студент должен видеть разрешенную цель, среду выполнения, ожидаемый результат, критерий остановки и sanitized evidence.

## Теория

### 1. Зачем SDET изучает эту тему

Тема `Занятие 1: Введение в Linux для пентестера` нужна не как отдельный набор команд, а как часть профессионального перехода от обычного QA/SDET к специалисту, который отвечает за качество и безопасность продукта. SDET уже привык проверять поведение системы, фиксировать воспроизводимые шаги, отделять факт от предположения и оформлять результат так, чтобы разработчик мог его повторить. В Security QA добавляется еще один слой: каждое действие должно быть разрешенным, ограниченным по scope и безопасным для данных, пользователей и инфраструктуры.

В этой лекции базовая задача состоит в том, чтобы понять модель `рабочая среда, терминальная дисциплина, файловая система, команды, evidence и аккуратная работа с локальными артефактами` и научиться превращать ее в проверяемый артефакт. Артефактом может быть команда, скриншот DevTools, HTTP history, лог, Markdown-заметка, JSON-вывод helper-скрипта, checklist или черновик finding. Главное требование: другой инженер должен понять, что было проверено, где, с каким разрешением и почему результат имеет значение.

### 2. Базовая модель урока

Модель этой темы можно читать как цепочку `цель -> действие -> наблюдение -> интерпретация -> решение`. Цель должна быть разрешенной: локальный файл, localhost, учебный lab, cloud lab, PortSwigger Academy, TryHackMe, HackTheBox или `https://olddev.slider-ai.ru` в рамках `education/slider_ai_scope.md`. Действие должно быть минимальным: сначала наблюдение и ручная проверка, затем low-rate инструмент, затем lab-only углубление. Наблюдение должно быть фактическим: строка вывода, статус HTTP, заголовок, имя файла, код возврата, сообщение ошибки или запись в отчете.

Интерпретация не равна выводу инструмента. Инструмент может сказать `open`, `possible`, `vulnerable`, `interesting`, но SDET обязан проверить контекст. Например, открытый порт сам по себе не является уязвимостью; это observation. Ошибка валидации может быть нормальным поведением; это not applicable. Неожиданный доступ к чужим данным может быть finding, но только если evidence sanitized и проверка не нарушила scope.

### 3. Термины, которые нельзя пропускать

`Target` — разрешенная цель проверки. Для курса это обычно локальная среда, lab или `https://olddev.slider-ai.ru`.

`Scope` — границы разрешенных действий. Scope отвечает на вопрос “что можно проверять, какими методами и когда нужно остановиться”.

`Evidence` — доказательство результата. Хорошее evidence содержит среду выполнения, цель, действие, фактический результат, интерпретацию и sanitization note.

`Observation` — безопасное наблюдение, которое может быть полезно, но еще не доказывает уязвимость.

`Finding` — подтвержденная проблема с влиянием, воспроизводимыми шагами и рекомендацией по исправлению.

`Requires approval` — статус для действия, которое потенциально допустимо в профессиональном тестировании, но не разрешено текущим scope.

`Lab-only` — техника, которую можно изучать только в учебной лаборатории или CTF, а не на продуктовой среде.

### 4. Безопасная рабочая среда

MacBook Air M2 с 8GB RAM используется как рабочая станция QA/пентестера. Это не значит, что все инструменты должны выполняться локально. Базовый путь новичка: macOS native, Homebrew или официальный installer, браузер, DevTools, Burp/ZAP в безопасном режиме, `curl`, `dig`, Python и локальные файлы. Этот путь снижает когнитивную нагрузку: студент учится видеть результат, а не бороться с виртуализацией.

Kali Linux ARM64 VM нужна как углубление, когда инструмент Linux/Kali-специфичен, нужна изоляция, снапшоты или сертификационная практика. На 8GB RAM VM должна получать 3-4GB RAM и 2 CPU. x86/x64 VirtualBox VM не является базовым путем на Apple Silicon. Для тяжелых сценариев используются cloud lab: TryHackMe AttackBox, HackTheBox/Pwnbox, PortSwigger Academy или другие легальные стенды.

### 5. Как выполнять практику без нарушения scope

Перед практикой студент делает короткую проверку разрешения. Первый вопрос: “Моя цель точно разрешена?” Второй: “Мое действие минимально для результата?” Третий: “Может ли действие создать нагрузку, изменить данные, перебрать учетные записи или раскрыть секреты?” Если ответ “да” или “не уверен”, действие получает статус `requires approval` и не выполняется на Slider AI.

Для `https://olddev.slider-ai.ru` допустимы только безопасные Security QA-действия: наблюдение поведения UI, DevTools, заголовки, ручная проверка валидации без destructive payloads, проверка сообщений об ошибках, сбор sanitized evidence, оформление test case и report draft. Запрещены DoS/load, brute force, destructive payloads, массовые wordlists, изменение чужих данных, попытки извлечения secrets и выход за scope.

### 6. Как читать результат

Результат читается не целиком, а по контрольным строкам. В командном выводе ищем версию инструмента, target, статус выполнения, ключевые строки результата и ошибки. В HTTP evidence смотрим method, URL path, status code, headers, cookies без секретных значений, redirect, cache/TLS признаки и response behavior. В браузере смотрим видимое поведение, сетевые запросы, сообщения в консоли и отсутствие лишних персональных данных в evidence.

Хорошая интерпретация отвечает на три вопроса. Что произошло фактически? Почему это важно для качества или безопасности? Какой следующий безопасный шаг? Например: “Получен `HTTP/2 200` от olddev, это подтверждает доступность стенда, но не является finding. Следующий шаг — зафиксировать baseline headers и не выполнять активные проверки без approval”.

### 7. Как оформлять evidence

Evidence должно быть коротким, проверяемым и безопасным. Минимальная форма:

```markdown
Environment: macOS native, Apple Silicon
Target: https://olddev.slider-ai.ru
Scope status: allowed observation
Action: checked response headers with curl -I
Observed result: HTTP status and selected sanitized headers captured
Interpretation: baseline observation, no vulnerability confirmed
Risk status: observation
Sanitization notes: cookies, tokens and personal data are not stored
```

Если результат получен в lab, target указывается как lab target, а не Slider AI. Если действие требовало бы intrusive-проверки на продуктовой среде, evidence фиксирует не выполнение атаки, а решение: `requires approval`, обоснование и безопасный lab-only follow-up.

### 8. Типичные ошибки новичка

Первая ошибка — запускать команду ради команды. В Security QA команда не имеет смысла без цели, scope и критерия сдачи.

Вторая ошибка — считать любой вывод инструмента подтвержденной уязвимостью. Большая часть вывода сначала является observation и требует проверки контекста.

Третья ошибка — смешивать macOS и Kali/Linux команды. Если команда использует `apt`, `ip addr`, Linux paths или root-only поведение, урок должен явно сказать, что это Kali/Linux или cloud lab.

Четвертая ошибка — сохранять слишком много данных. Evidence должно быть sanitized: без cookies, JWT, паролей, приватных ключей, персональных данных и чужих секретов.

Пятая ошибка — переносить lab-техники на Slider AI. То, что разрешено в CTF, не становится автоматически разрешенным на тестовом стенде продукта.

### 9. Связь с предыдущими и следующими уроками

Эта тема опирается на уже изученные SDET-навыки: аккуратная работа с файлами, повторяемые команды, понимание входных требований, фиксация ожидаемого и фактического результата. В следующих уроках тот же принцип будет расширяться: из отдельных действий получится test plan, из наблюдений — triage, из повторяемых шагов — regression checklist, из helper-скриптов — поддерживаемая security automation.

Поэтому в текущем уроке важно не только выполнить практику, но и объяснить ее. Студент должен уметь сказать: “Я выбрал такую цель, потому что она разрешена; я выбрал такой режим, потому что он минимален; я получил такой результат; это observation/finding/not applicable; следующий шаг безопасен или требует approval”.

### 10. Минимальная профессиональная планка

Лекция считается освоенной, когда студент может без внешнего поиска объяснить модель темы, выполнить обязательный безопасный путь, получить эталонный вывод, интерпретировать его и оформить sanitized evidence. Для SDET это и есть переход от “я попробовал инструмент” к “я провел контролируемую Security QA-проверку”.

Для темы `Занятие 1: Введение в Linux для пентестера` минимальная планка такая: студент понимает рабочая среда, терминальная дисциплина, файловая система, команды, evidence и аккуратная работа с локальными артефактами, выполняет безопасную практику в среде `macOS native, локальные папки, локальные файлы и учебные заметки; Slider AI используется только как объект планирования evidence`, объясняет результат через воспроизводимые действия, контроль рабочей директории, хранение артефактов тестирования, чтение вывода и логов и не выходит за ограничения Slider AI. Все, что требует более агрессивной техники, переносится в углубление после изучения следующих уроков или оформляется как `requires approval`.

### 11. Контроль понимания перед практикой

Перед переходом к заданиям студент должен остановиться и проговорить тему как инженерную процедуру. Нужно назвать разрешенную цель, среду выполнения, минимальное действие, ожидаемый безопасный результат и критерий остановки. Если хотя бы один пункт неясен, практика не начинается: сначала уточняется scope или выбирается локальная лабораторная цель. Такой контроль снижает риск случайно выполнить активную проверку там, где требовалось только наблюдение.

Второй контрольный вопрос: какие данные попадут в evidence? В отчет нельзя переносить cookies, токены, персональные данные, приватные ключи, полные ответы с секретами и любые сведения, которые не нужны для доказательства результата. Хороший SDET собирает ровно столько фактов, сколько нужно для воспроизведения и принятия решения.


### 12. Предметная часть урока

Для темы `Занятие 1: Введение в Linux для пентестера` важно освоить не абстрактный “Linux”, а рабочий минимум инженера. Команда всегда выполняется в конкретной директории, от конкретного пользователя и с конкретными правами. Поэтому перед любым действием проверяются `pwd`, `whoami`, путь к файлу и ожидаемый результат. Для macOS базовые команды совпадают с Unix-подходом, но некоторые флаги отличаются от GNU/Linux; если пример зависит от Linux, он помечается как Kali/Linux.

Файловые операции читаются как evidence workflow. `mkdir` создает место для артефактов, `touch` подготавливает файл, `cat` и `less` позволяют прочитать результат, `grep` помогает найти строку, `wc` оценивает объем, `>` перезаписывает, а `>>` добавляет без потери предыдущих записей. Для SDET это та же дисциплина, что в автотестах: входные данные, действие, фактический результат, артефакт и критерий сдачи.

Главное ограничение: команды удаления, изменения прав и массовой обработки сначала применяются только к учебной папке. Нельзя запускать опасные действия из корня проекта, домашней директории или папок браузера без понимания последствий. На Slider AI в этом блоке не выполняются атаки: студент готовит локальные заметки, структуру evidence и правила sanitization.

3. Проверьте, где вы находитесь и какая у вас архитектура.
4. Сохраните минимальный evidence в Markdown.

### Шаг 2: Проверить среду

На macOS:

```bash
uname -m
sw_vers
whoami
echo "$SHELL"
echo "$PATH"
which python3
python3 --version
```

Пример вывода:

```text
arm64
ProductName:            macOS
ProductVersion:         14.5
BuildVersion:           23F79
student
/bin/zsh
/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin
/opt/homebrew/bin/python3
Python 3.12.3
```

Как читать:

- `arm64` подтверждает Apple Silicon;
- `ProductVersion` показывает версию macOS;
- `whoami` показывает текущего пользователя, от имени которого будут создаваться файлы.
- `SHELL` показывает командную оболочку;
- `PATH` показывает, где shell ищет программы;
- `which python3` показывает конкретный исполняемый файл Python;
- `python3 --version` фиксирует версию инструмента для воспроизводимости.

В Kali/Ubuntu VM, если вы уже используете углубление:

```bash
uname -m
cat /etc/os-release
whoami
echo "$SHELL"
which python3
python3 --version
```

Пример вывода:

```text
aarch64
PRETTY_NAME="Kali GNU/Linux Rolling"
ID=kali
student
/bin/bash
/usr/bin/python3
Python 3.11.8
```

Пояснение: здесь `cat > file <<'EOF'` используется как безопасный способ создать учебный текстовый файл. Маркер `EOF` означает конец вводимого текста. В реальной работе такой файл можно создать и через редактор.

### Шаг 6: Сохранить диагностический снимок среды

Создайте отдельный evidence-файл:

```bash
{
  echo "## Environment snapshot"
  echo "pwd: $(pwd)"
  echo "user: $(whoami)"
  echo "arch: $(uname -m)"
  echo "shell: $SHELL"
  echo "python3_path: $(which python3)"
  echo "python3_version: $(python3 --version)"
} > evidence/lesson_01_environment.txt
```

Откройте его:

```bash
cat evidence/lesson_01_environment.txt
```

Пример вывода:

```text
## Environment snapshot
pwd: /Users/student/slider-ai-pentest
user: student
arch: arm64
shell: /bin/zsh
python3_path: /opt/homebrew/bin/python3
python3_version: Python 3.12.3
```

Как читать:

- `pwd` подтверждает, что evidence собран внутри workspace;
- `user` подтверждает, что работа идет не от `root`;
- `arch` показывает Apple Silicon;
- `shell` пригодится при будущей отладке скриптов;
- `python3_path` и `python3_version` делают Python-среду воспроизводимой.

### Шаг 7: Проверить, что sensitive evidence не появился случайно

В первом уроке секретов быть не должно. Выполните локальную самопроверку заметки:

```bash
grep -Ei "password|token|secret|cookie|authorization" notes/lesson_01.md || echo "No obvious secrets in lesson_01.md"
```

Пример безопасного вывода:

```text
No obvious secrets in lesson_01.md
```

Важно: это не “сканер безопасности”. Это простая привычка самопроверки перед тем, как показать evidence преподавателю, разработчику или менеджеру.

## Примеры вывода

Минимальный эталонный артефакт для сдачи по теме `Занятие 1: Введение в Linux для пентестера`:

```markdown
Environment: macOS native, Apple Silicon
Target: https://olddev.slider-ai.ru
Scope status: allowed observation within education/slider_ai_scope.md
Action: safe manual or low-impact check from this lesson
Evidence:
  - Command or browser path is recorded.
  - Output contains only sanitized technical lines.
  - Cookies, tokens, passwords and personal data are not stored.
Observed result: baseline behavior captured without destructive action
Interpretation: observation; no vulnerability is confirmed without additional proof
Next step: document result, request approval for intrusive follow-up, or repeat in lab-only environment
```

Пример локального вывода для обязательного безопасного пути:

```text
Environment: macOS native
Target: local workspace or explicitly allowed olddev observation
Result status: observation
Evidence saved: evidence/current_lesson/notes.md
Sanitization: secrets and personal data excluded
```

Такой вывод считается эталонным не потому, что строки всегда будут идентичными, а потому что в нем есть все обязательные элементы профессионального evidence: среда, разрешенная цель, действие, наблюдение, интерпретация, sanitization и следующий безопасный шаг.

## Адаптация под macOS (M2, 8GB)

- Основной путь: macOS Terminal, Homebrew, официальный Python, браузер, DevTools, Burp/ZAP по мере уроков.
- Kali VM не обязательна в первом уроке.
- Если VM нужна позже, используйте ARM64-образ и выделяйте 3-4GB RAM максимум.
- Не используйте x86/x64 VM как базовый путь на Apple Silicon.
- Homebrew на Apple Silicon обычно находится в `/opt/homebrew`.
- Для Python-инструментов позже используйте `pipx`, `pip3` или virtualenv, а не случайную глобальную установку.

## Частые ошибки

1. **Начинать с Kali как обязательного пути.** На MacBook Air M2 это часто создает лишнюю сложность. Сначала достаточно macOS native.
2. **Хранить evidence в случайных папках.** Через неделю невозможно понять, что относится к какому уроку или проверке.
3. **Смешивать учебную цель и продукт.** В первом уроке Slider AI только фиксируется как разрешенная цель будущих заданий.
4. **Писать секреты в заметки.** Evidence должен быть sanitized.
5. **Не фиксировать среду.** Без версии ОС, архитектуры и пути сложно повторить результат.
6. **Не понимать `PATH`.** Если shell запускает не ту версию Python или инструмента, результаты будущих уроков будут отличаться.
7. **Использовать `sudo` как универсальное лекарство.** Это скрывает реальную причину проблемы и может испортить права.
