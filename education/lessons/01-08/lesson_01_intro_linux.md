## Source-driven theory

Из книг курса взята не «домашняя ссылка», а методика: профессионал сначала настраивает среду, проверяет инструменты, фиксирует наблюдения и только потом выполняет практику. В SDET это проявляется как воспроизводимый test run. В Security QA это становится еще важнее, потому что каждое действие должно иметь границы разрешения, evidence и объяснение риска.

Главная мысль урока: пентест начинается не с атаки. Он начинается с управляемой рабочей станции.

Если рабочая среда хаотична, студент быстро сталкивается с типичными ошибками:

- команда была выполнена, но непонятно где;
- вывод потерян, а значит результат нельзя приложить к отчету;
- инструмент установлен непонятным способом и не воспроизводится;
- учебная команда случайно применяется к реальному продукту;
- macOS, Kali и cloud lab смешиваются в одной инструкции без понимания различий.

В этом курсе мы строим противоположную привычку: каждое действие имеет среду, цель, команду, evidence, интерпретацию и следующий безопасный шаг.

## Теория

### 1. Что такое Linux-подход и почему он нужен QA/SDET

Linux для пентестера — это не только операционная система. Это способ работать с системой через текстовые команды, файлы, процессы, права, сеть и логи. Security QA постоянно сталкивается с вопросами, которые удобнее решать именно так:

- где лежит файл конфигурации;
- какой процесс слушает порт;
- какой HTTP-запрос был отправлен;
- какой лог подтверждает ошибку;
- как повторить проверку без ручной магии;
- как сохранить доказательство так, чтобы его понял разработчик.

SDET уже привык мыслить воспроизводимостью: тест должен запускаться повторно и давать понятный результат. В security-практике эта привычка переносится на ручные и полуавтоматические проверки. Неважно, используете вы браузер, Burp, ZAP, Python helper или `curl`: результат должен быть объяснимым.

### 2. Базовая модель Unix-системы

Чтобы не заучивать команды как магические заклинания, нужно понимать простую модель Unix-подобной системы. macOS и Linux отличаются деталями, но базовые идеи похожи.

| Уровень | Что это такое | Что видит QA/Security QA |
|---|---|---|
| Hardware | процессор, память, диск, сеть | архитектура `arm64`, объем RAM, сетевой интерфейс |
| Kernel | ядро ОС, управляющее процессами, файлами, памятью, сетью | ошибки прав, процессы, порты, системные ограничения |
| System libraries | библиотеки, через которые программы обращаются к ОС | разные сборки пакетов на macOS/Linux |
| Shell | командная оболочка пользователя | `zsh`, `bash`, команды, переменные окружения |
| User programs | терминальные и графические программы | `python3`, `git`, `curl`, браузер, Burp, ZAP |
| Files and logs | конфигурация, артефакты, журналы | evidence, troubleshooting, отчеты |

Когда студент вводит команду:

```bash
python3 --version
```

происходит не “терминал знает Python”. Shell ищет исполняемый файл `python3` в списке директорий из переменной `PATH`, запускает найденную программу, программа обращается к системным библиотекам и ядру, а результат возвращается в стандартный вывод.

Эта модель нужна с первого занятия, потому что почти все будущие проблемы будут выглядеть так:

- команда не найдена;
- команда есть, но запускается не та версия;
- на macOS флаг команды отличается от Linux;
- инструмент установлен, но shell его не видит;
- программа не имеет прав на файл;
- вывод ушел не туда и evidence потерян;
- команда выполнилась в другой директории.

Если студент понимает уровни системы, он не паникует, а задает правильный диагностический вопрос: “что именно не сработало: путь, права, версия, среда, сеть, файл или ожидание?”

### 3. Terminal, shell и команда — не одно и то же

Терминал — это окно или приложение, через которое вы вводите текст. Shell — программа внутри терминала, которая интерпретирует команды. Команда — конкретное действие, которое shell запускает или выполняет сам.

На macOS обычно используется `zsh`. В Kali/Ubuntu чаще встречается `bash`. Для первых уроков разница небольшая, но важно не смешивать понятия:

- Terminal.app или iTerm2 — приложение;
- `zsh` или `bash` — shell;
- `ls`, `pwd`, `python3`, `git` — команды;
- `~/slider-ai-pentest` — путь;
- `PATH`, `HOME`, `SHELL` — переменные окружения.

Проверить текущую shell:

```bash
echo "$SHELL"
```

Пример вывода:

```text
/bin/zsh
```

Проверить, где shell ищет программы:

```bash
echo "$PATH"
```

Пример вывода на macOS Apple Silicon:

```text
/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin
```

Как читать: shell будет искать команду слева направо. Если в `/opt/homebrew/bin` есть `python3`, а в `/usr/bin` тоже есть `python3`, будет запущен тот вариант, который встретился раньше.

Для SDET это знакомая проблема версий зависимостей. Для Security QA она критична: разные версии `python3`, `nmap`, `curl`, `git`, `openssl` или `zap` могут давать разные результаты и разные флаги.

### 4. Стандартные потоки: stdin, stdout, stderr

Unix-инструменты хорошо комбинируются, потому что многие из них работают с тремя стандартными потоками:

| Поток | Назначение | Пример |
|---|---|---|
| stdin | входные данные программы | текст, переданный через pipe |
| stdout | обычный результат работы | список файлов, версия программы |
| stderr | ошибки и диагностические сообщения | `No such file or directory` |

В уроке 2 вы подробно изучите перенаправление и pipe, но уже сейчас нужно понять принцип: команда не просто “печатает на экран”. Она пишет в поток. Этот поток можно сохранить как evidence, передать другой команде или отделить от ошибок.

Простой пример:

```bash
pwd
```

`pwd` пишет текущий путь в stdout.

Если путь сохранить:

```bash
pwd > evidence/location.txt
```

stdout попадает в файл. Так рождается минимальный evidence.

Почему это важно для пентеста: инструменты безопасности часто выводят много информации. Если студент не понимает потоки, он будет делать скриншоты всего подряд или терять важные строки. Профессиональнее сохранять минимальный, очищенный, воспроизводимый фрагмент.

### 5. Пользователь, права и root на уровне первого урока

Подробно права будут в уроке 3, но базовую картину нужно понимать сразу.

В Unix-подобной системе почти каждое действие выполняется от имени пользователя. Команда:

```bash
whoami
```

показывает текущего пользователя.

Обычный пользователь должен работать в своей домашней директории и учебном workspace. Суперпользователь `root` или команда `sudo` нужны только для административных действий: установка системных пакетов, изменение системной конфигурации, работа с некоторыми службами.

Правило курса:

- не использовать `sudo`, если команда работает без него;
- не запускать неизвестные команды с `sudo`;
- не исправлять ошибки прав через “дать все права всем”;
- не работать от `root` как обычный пользователь;
- не хранить evidence в системных директориях.

Типичная плохая привычка новичка:

```bash
sudo chmod -R 777 .
```

В этом курсе такая команда считается ошибкой методологии. Она может скрыть реальную проблему прав, испортить безопасность файлов и научить опасному паттерну. Security QA должен понимать ограничение, а не ломать его.

### 6. Где живут программы и почему `which` важен

Когда вы вводите:

```bash
python3
```

shell ищет программу в `PATH`. Чтобы увидеть, какой именно файл будет запущен:

```bash
which python3
```

Пример для macOS:

```text
/opt/homebrew/bin/python3
```

Пример для Kali/Ubuntu:

```text
/usr/bin/python3
```

Это объясняет важную мысль из книги про PyCharm и рабочие среды: одна и та же программа в разных ОС может быть собрана и установлена по-разному. Python-пакеты, инструменты CLI и зависимости не существуют “вообще”; они существуют в конкретной среде.

Для курса это превращается в правило evidence:

```markdown
Tool version:
- python3: Python 3.12.x
- path: /opt/homebrew/bin/python3
- OS: macOS arm64
```

Без версии инструмента и среды отчет слабее. Разработчик или преподаватель не сможет понять, почему у него результат отличается.

### 7. macOS, Linux и Kali: кто за что отвечает

На MacBook Air M2 основной безопасный путь новичка — macOS native. Это значит, что первые уроки выполняются в обычном Terminal, без обязательной виртуальной машины. Такой путь проще, быстрее и меньше нагружает 8GB RAM.

macOS подходит для:

- базовой навигации по файловой системе;
- ведения заметок и evidence;
- Git, Python, Homebrew, браузера и DevTools;
- Burp/ZAP в базовых web-сценариях;
- безопасных запросов к разрешенному тестовому стенду.

Kali Linux ARM64 VM нужна не как «магическая ОС хакера», а как изолированная лаборатория. Она полезна, когда инструмент лучше поддерживается в Linux, когда нужна Kali-специфичная поставка, когда требуется snapshot или когда упражнение имитирует экзаменационную среду.

На MacBook Air M2 с 8GB RAM безопасная настройка VM:

- ARM64-образ, а не x86/x64 как базовый путь;
- 2 CPU;
- 3-4GB RAM максимум;
- 20-40GB диска;
- snapshot чистой системы после установки;
- закрытие тяжелых приложений на macOS перед запуском VM.

Cloud lab используется, когда локальная машина не должна тащить тяжелые сценарии: TryHackMe AttackBox, HackTheBox Pwnbox, PortSwigger Academy и другие легальные стенды.

Выбор среды должен быть осознанным:

| Ситуация | Среда | Почему |
|---|---|---|
| Учимся навигации и evidence | macOS native | быстро, безопасно, не требует VM |
| Нужен Linux-only инструмент | Kali ARM64 VM | изоляция и совместимость |
| Нужны snapshots и откат | Kali ARM64 VM | можно вернуть чистое состояние |
| Тяжелая CTF/экзаменационная практика | cloud lab | не перегружает MacBook 8GB |
| Проверка Slider AI olddev в web-scope | macOS native + browser/Burp/ZAP | достаточно для большинства web-QA задач |

### 8. Файловая система как карта рабочей среды

В Unix-подобных системах файловая система выглядит как дерево. В Windows пользователь часто думает через диски `C:` и `D:`. В Linux и macOS есть единый корень `/`, от которого расходятся каталоги.

Ключевые идеи:

- `/` — корень дерева;
- `~` — домашняя директория текущего пользователя;
- `.` — текущая директория;
- `..` — родительская директория;
- имена файлов чувствительны к регистру во многих Linux-средах;
- скрытые файлы начинаются с точки, например `.zshrc`;
- путь может быть абсолютным или относительным.

Абсолютный путь начинается от корня или домашней директории:

```text
/Users/alex/slider-ai-pentest/notes/lesson_01.md
~/slider-ai-pentest/notes/lesson_01.md
```

Относительный путь считается от текущей директории:

```text
notes/lesson_01.md
../evidence
```

Для Security QA это не теория ради теории. Ошибка в пути часто означает потерянный evidence, запуск команды не в той папке или загрязнение рабочего проекта временными файлами.

### 9. Типовые директории Linux и безопасное сравнение с macOS

Linux-директории, которые важно узнавать:

| Директория | Назначение | Что важно Security QA |
|---|---|---|
| `/etc` | Конфигурация системы и сервисов | искать настройки только в своей lab-среде |
| `/var` | Изменяемые данные: логи, кэш, очереди | логи помогают подтверждать события |
| `/home` | Домашние директории пользователей | пользовательские файлы и права |
| `/root` | Домашняя директория суперпользователя | не путать с `/`; доступ ограничен |
| `/tmp` | Временные файлы | часто используется инструментами; не хранить evidence |
| `/usr/bin`, `/bin` | исполняемые программы | помогает понять, откуда запускается команда |
| `/proc`, `/sys` | виртуальная информация о ядре и процессах | в macOS отсутствует в таком виде |

В macOS структура похожа идеей дерева, но отличается деталями. Домашняя директория обычно находится в `/Users/<name>`, пакетный менеджер Homebrew на Apple Silicon часто использует `/opt/homebrew`, а многие Linux-команды имеют BSD-варианты с отличающимися флагами.

Практический вывод: если команда из Linux-инструкции не сработала на macOS, это не всегда ошибка студента. Возможно, команда отличается между GNU/Linux и BSD/macOS. В курсе такие различия фиксируются как часть troubleshooting.

### 10. Evidence workspace

Evidence workspace — это не просто папка. Это место, где студент хранит доказательства так, чтобы их можно было проверить и безопасно показать команде.

Минимальная структура:

```text
~/slider-ai-pentest/
├── notes/
├── evidence/
├── screenshots/
├── requests/
├── scripts/
└── tmp/
```

Назначение:

- `notes/` — учебные заметки, выводы, ответы на вопросы;
- `evidence/` — фрагменты вывода команд, sanitized HTTP history, результаты проверок;
- `screenshots/` — скриншоты без секретов и персональных данных;
- `requests/` — сохраненные HTTP-запросы или описания ручных действий;
- `scripts/` — свои безопасные helpers;
- `tmp/` — временные файлы, которые можно удалить.

Правило: evidence не должен содержать токены, пароли, приватные ключи, персональные данные пользователей, чужие cookies или секреты приложения.

### 11. Evidence как инженерный артефакт, а не “скриншот на память”

Evidence должен отвечать на пять вопросов:

1. Где выполнялась проверка?
2. Какая цель была разрешена?
3. Что именно было сделано?
4. Какой фактический результат получен?
5. Почему этот результат имеет значение?

Плохой evidence:

```markdown
Все работает.
```

Такой текст нельзя проверить.

Лучше:

```markdown
Environment: macOS native, arm64
Target: local workspace only
Command: pwd
Output: /Users/student/slider-ai-pentest
Interpretation: commands are being executed inside the approved local course workspace.
Status: observation
```

Это еще не finding и не уязвимость. Но это хорошая инженерная запись: ее можно повторить, проверить и использовать как основу для следующих уроков.

### 12. Threat model первого урока: что может пойти не так

Даже подготовка рабочей станции имеет риски:

| Риск | Пример | Как предотвращаем |
|---|---|---|
| Потеря evidence | вывод команды остался только в scrollback терминала | сохраняем минимальный вывод в `notes/` или `evidence/` |
| Секреты в заметках | случайно сохранен cookie, token, private key | применяем sanitized evidence |
| Неверная среда | команда выполнена в production shell или не той VM | фиксируем `Environment` и `Target` |
| Несовместимость команд | Linux-флаг не работает на macOS | пишем troubleshooting-наблюдение |
| Случайный выход за scope | активная команда отправлена на неразрешенный домен | в каждом артефакте есть `Target` и `Boundary` |
| Невоспроизводимость | неизвестна версия инструмента | сохраняем `tool --version` и `which tool` |

Этот маленький threat model нужен не для бюрократии. Он показывает профессиональное мышление: Security QA управляет риском даже в собственном процессе проверки.

### 13. Граница Slider AI

В этом уроке Slider AI не тестируется. Мы только записываем разрешенную цель и правила:

- разрешенный стенд: `https://olddev.slider-ai.ru`;
- production не входит в учебное задание;
- DoS/load, brute force, destructive payloads и изменение чужих данных запрещены;
- активные проверки выполняются только в тех уроках, где они явно разрешены и описаны безопасно;
- если действие непонятно, оно получает статус `requires approval`.

Эта дисциплина важнее, чем кажется. Профессиональный Security QA отвечает не только за найденные уязвимости, но и за то, чтобы сам процесс проверки не создавал риск для продукта.

### Шаг 2: Проверить среду


Как читать:

- `arm64` подтверждает Apple Silicon;

- `PATH` показывает, где shell ищет программы;
- `which python3` показывает конкретный исполняемый файл Python;
- `python3 --version` фиксирует версию инструмента для воспроизводимости.

В Kali/Ubuntu VM, если вы уже используете углубление:

```bash

whoami

which python3
python3 --version
```

```text
student

/usr/bin/python3
```

## Частые ошибки

1. **Начинать с Kali как обязательного пути.** На MacBook Air M2 это часто создает лишнюю сложность. Сначала достаточно macOS native.
2. **Хранить evidence в случайных папках.** Через неделю невозможно понять, что относится к какому уроку или проверке.
3. **Смешивать учебную цель и продукт.** В первом уроке Slider AI только фиксируется как разрешенная цель будущих заданий.
4. **Писать секреты в заметки.** Evidence должен быть sanitized.
5. **Не фиксировать среду.** Без версии ОС, архитектуры и пути сложно повторить результат.
6. **Не понимать `PATH`.** Если shell запускает не ту версию Python или инструмента, результаты будущих уроков будут отличаться.
7. **Использовать `sudo` как универсальное лекарство.** Это скрывает реальную причину проблемы и может испортить права.
